DeliveredPersonal lab · private repository

DataOps Lab: an end-to-end analytical pipeline

Capstone lab of a Data Engineering program: an analytical pipeline executed end to end over a transactional PostgreSQL database running in Docker. Airbyte replicates the tables into the Snowflake RAW layer, dbt standardizes them and builds the dimensional model across STAGING, INT and DW, and Airflow coordinates the cycle (source freshness, sync, dbt build and reconciliation against the source) before consumption in Power BI.

Evidence and limits: lab completed and delivered. 22 dbt models over a fact table of 16,044 rows; dbt build finishes with 136 passing tests and no warnings in both execution environments, local and containerized. Personal data stays out of the analytical model and every layer runs with the least privilege it needs. The repository is private, so these numbers are not publicly verifiable; I demonstrate them in a conversation.

My role

Individual, self-directed project: capstone lab of the Data Engineering program, from the Docker infrastructure to the dashboard.

Technical decisions

  • Separate layers in Snowflake. RAW keeps what Airbyte delivered; STAGING and DW are rebuilt by dbt. The source stays auditable and consumption stays stable.
  • Reconcile against the source, not between layers. The DAG compares the row counts of the 15 PostgreSQL tables with RAW and fails on any divergence. The internal reconciliation compared two sides of the same load: had Airbyte brought 90% of the rentals, both sides would agree at 90%.
  • Two dbt targets. A local build used to write straight into the schemas Power BI reads. With dev and prod separated, a test never overwrites what the report consumes.
  • One service user with an RSA key per tool. Airbyte and dbt have distinct passwordless users, each with the least privilege of its layer.
  • Personal data out of the DW. The customer dimension stopped publishing street address, postal code and phone: no measure used those columns, and the Power BI reader role could see them purely by inertia.

Outcome

22 dbt models and 136 tests: keys, 21 relationships between staging models, grain of bridge tables, business rules and reconciliation. Freshness on all 15 sources, warning at 24 h and error at 48 h. A Power BI dashboard with 15 DAX measures. Private repository: demonstrated in a conversation.

Lessons learned

  • A calendar derived from observed dates has gaps and makes DATEADD return wrong values silently; the date dimension needs to be a contiguous spine, with a test that blocks regressions.
  • The reconciliation that matters is against the source. Comparing two layers derived from the same load only proves the load is consistent with itself.

DeliveredCorporate project · public reconstruction

Tax Document Processing Orchestration

A Power Apps Canvas application that receives batches of tax invoices through spreadsheet import. A Power Automate flow validates the file and records each row as a job in Dataverse; Power Automate Desktop robots consume the queue, register the invoice on the regulatory portals and return the outcome, which the operator follows on the same screen. Every job has an idempotency key and is claimed before it runs: resubmitting a batch does not duplicate processing.

Scope statement: the project was delivered with import through the app, a queue in Dataverse, execution by the robots and status lookup in operation. The public repository is a reconstruction: the queue contract, diagram, sample data and test scenarios were rewritten from scratch, with no real environment, portal, credential or document.

Technical decisions

  • An idempotency key per job. Each imported row becomes a job with its own key; resubmitting the batch creates no duplicates.
  • A claim that expires. The worker claims the job with a lock that expires; if it never confirms execution, the job returns to the queue with no manual intervention.
  • Bounded retries and traceable failure. A temporary failure goes back to the queue up to the attempt limit; a definitive failure is recorded with correlation and logs.
  • Workers only get compatible jobs, and never secrets. Portal credentials and parameters live in a vault and environment variables; the job payload does not carry them.
  • Operators see status and summary, not the automation. The screen follows the outcome of each job without exposing documents, portals or sensitive evidence.

Outcome

In operation, with import through the app, a queue in Dataverse, execution by the robots and status lookup. Volume, cycle time and number of portals are not published.

Lessons learned

  • Separating who submits the batch from who processes it is what makes safe reprocessing possible: the operator resubmits, the queue decides.
  • Explicit states (pending, claimed, running, retry pending, failed) turn monitoring into a query instead of an investigation.

DeliveredAcademic project · public repository

Brazilian Chamber of Deputies — Lakehouse Pipeline

A Lakehouse implemented on Databricks for the open data of the Brazilian Chamber of Deputies. A Python collector queries 17 endpoints configured in YAML, preserves an auditable origin and promotes the data through Bronze, Silver and Gold for analytical consumption in Power BI.

Evidence: the Lakehouse runs on Databricks with Unity Catalog Volume, PySpark and Delta; the local environment supports development and testing. 48 automated tests and continuous validation on GitHub.

My role

Individual final project of a Data Engineering program (Upskill Tiller, cohort 2): collection, modeling, tests, documentation and publication.

Technical decisions

  • Medallion instead of direct ELT or Data Vault. Bronze keeps the raw payload, so reprocessing Silver and Gold never requires going back to the API. Data Vault would be overkill for the volume and cadence.
  • Endpoint catalog in YAML. The 17 endpoints are data, not code: adding one means adding a block, with its incremental strategy declared and validated in a dataclass.
  • PySpark on Databricks, pandas in CI. The same sequence of operations runs in pandas locally in about 6 seconds, without a cluster, and in native PySpark on Databricks.
  • Audit embedded in every record. Every Bronze row carries the ingestion timestamp, endpoint, source URL, page, run identifier and payload hash; lineage does not depend on a join with a control table.

Outcome

Six mandatory analytical deliverables and two optional ones (vote streaming and change data capture of bill progress with SCD2), 48 automated tests across six modules and continuous validation on GitHub Actions. Public repository.

Lessons learned

  • A repository that runs in three modes (local pandas, local PySpark and Databricks) only holds up if the logic is the same in all three and CI proves it on every push.
  • Per-record audit costs columns, but it removes the question “where did this row come from?” in the middle of an incident.

In acceptance testingCorporate project · anonymized case

OTP authentication RPA with OIDC token persistence

A Power Automate Desktop robot that renews OIDC tokens for multiple accounts. It uses HTTP wherever an API exists and falls back to the browser only for login, OTP and token capture; after verification, the internal service distributes the token through Redis with a TTL.

Evidence and limits: validated end to end in the acceptance environment, with multi-account processing, failures isolated per account and operational error classification. The public case keeps environments, portals, endpoints and credentials anonymized.

Technical decisions

  • HTTP where an API exists, browser only where it doesn't. OAuth2 authentication, the account list, the OTP lookup and the token write are HTTP calls; the browser steps in for login, OTP and reading localStorage. Every step kept out of the browser is a step that doesn't break when the portal changes a CSS class.
  • Failure isolated per account. Each account runs inside an error-handling block: an invalid password or a missing OTP doesn't bring the whole run down, and the final summary classifies failures by cause.
  • Verify after writing. After the PUT, a GET confirms the token is readable by the integrations: persistence only counts once it has been read back.

Outcome

Validated end to end in acceptance testing, with about twelve accounts per run and a cycle of roughly 70 seconds per account. Production and real volume are not published.

Lessons learned

  • The constraint defines the design: with ROPG blocked, a token born in the browser and a short-lived OTP, the order login → challenge → lookup → typing is not a choice, it is the only possible sequence.
  • Before automating the screen, spend the validation phase finding out what the API already solves: here it was half of the steps.

Architecture documentedAcademic project · postgraduate program

Integrated Data Platform on AWS

A layered architecture on Amazon S3, with an ETL pipeline and Medallion organization, developed as the applied project of the postgraduate program in Data Engineering and Architecture with an Emphasis on AI. The scenario simulates a mining operation (fuel control and fleet maintenance in an ERP, IoT telemetry of cargo movement, API integrations and geology and laboratory files), chosen because it concentrates systems that do not talk to each other.

Scope statement: individual academic project completed in 2025. The mining company is a simulated scenario and the data is fictitious; nothing here came from a corporate or third-party system. The diagram represents the proposed architecture, not a production environment.

My role

Individual applied project of the postgraduate program: survey of the sources, design of the layers and of the cross-cutting controls.

Technical decisions

  • Bronze receives data as it arrives. Every source lands without transformation, preserving traceability and the basis for reprocessing.
  • Silver concentrates standardization. Typing, treatment and validation live in a single layer, so Gold never has to fix data.
  • Governance spans all three layers. Catalog, access control, quality and monitoring are a condition of every stage, not a stage of their own.

Outcome

Architecture proposed and documented; no execution, load or environment.

Lessons learned

  • In an operation with an ERP, telemetry, APIs and spreadsheets, the problem is not volume, it is data that doesn't talk. The Bronze layer exists to accept everything before deciding what to standardize.
