DataOps Lab: an end-to-end analytical pipeline

Capstone lab of a Data Engineering program: an analytical pipeline executed end to end over a transactional PostgreSQL database running in Docker. Airbyte replicates the tables into the Snowflake RAW layer; dbt standardizes them in STAGING, which also holds the intermediate views, and builds the dimensional model in DW. Airflow coordinates the cycle (source freshness, sync, reconciliation against the source and dbt build) before consumption in Power BI.

Evidence and limits: lab executed end to end, from the source database to the dashboard, with one complete manual run of the Airflow DAG. 22 dbt models over a fact table of 16,044 rows; dbt build finishes with 114 passing tests and no warnings in both execution environments, local and containerized. Customer street address, postal code and phone stay out of the analytical model, and every layer runs with the least privilege it needs. The repository is private, so these numbers are not publicly verifiable; I demonstrate them in a conversation.

My role

Individual, self-directed project: capstone lab of the Data Engineering program, from the Docker infrastructure to the dashboard.

Technical decisions

  • Separate layers in Snowflake. RAW keeps what Airbyte delivered; STAGING and DW are rebuilt by dbt. The source stays auditable and consumption stays stable.
  • Reconcile against the source, not between layers. The DAG compares the row counts of the 15 PostgreSQL tables with RAW and fails on any divergence. The internal reconciliation compared two sides of the same load: had Airbyte brought 90% of the rentals, both sides would agree at 90%.
  • Two dbt targets. A local build used to write straight into the schemas Power BI reads. With dev and prod separated, a test never overwrites what the report consumes.
  • One service user with an RSA key per tool. Airbyte and dbt have distinct passwordless users, each with the least privilege of its layer.
  • Street address, postal code and phone out of the DW. The customer dimension stopped publishing those three columns: no measure used them, and the Power BI reader role could see them purely by inertia. Name, district, city and country stayed, which support geographic analysis without locating anyone's home.

Outcome

114 dbt tests: keys, 21 relationships between staging models, grain of bridge tables, business rules and reconciliation. Freshness on all 15 sources, warning at 24 h and error at 48 h. A Power BI dashboard with 15 DAX measures.

Lessons learned

  • A calendar derived from observed dates has gaps and makes DATEADD return wrong values silently; the date dimension needs to cover every day, with no gaps, and a test that blocks regressions.
  • A freshness check that runs after the sync measures the timestamp the sync itself just wrote, so it can only fail if the sync already failed. Run before the sync, it measures the real lag of the source.

Brazilian Chamber of Deputies — Lakehouse Pipeline

A Lakehouse implemented on Databricks for the open data of the Brazilian Chamber of Deputies. A Python collector queries 17 endpoints configured in YAML, writes the raw payload with audit metadata and promotes the data through Bronze, Silver and Gold into analytical tables ready for BI and SQL consumption.

Evidence: the Lakehouse runs on Databricks with Unity Catalog Volume, PySpark and Delta; the local environment supports development and testing.

My role

Individual final project of a Data Engineering program (Upskill Tiller, cohort 2): collection, modeling, tests, documentation and publication.

Technical decisions

  • Medallion instead of direct ELT or Data Vault. Bronze keeps the raw payload of the latest collection, so reprocessing Silver and Gold does not require going back to the API. Data Vault would be overkill for the volume and cadence.
  • Endpoint catalog in YAML. The 17 endpoints are data, not code: adding one means adding a block, validated in a dataclass when the catalog is loaded.
  • PySpark on Databricks, pandas in CI. The notebooks reimplement the logic in native PySpark; locally, the same sequence (rename, cast, deduplicate) runs in pandas, and CI tests it in about 6 seconds with no Spark or JDK on the machine. The cost is keeping the logic in two places, and the tests only cover the pandas version.
  • Audit embedded in every record. Every Bronze row carries the ingestion timestamp, endpoint, source URL, page, run identifier and payload hash; lineage does not depend on a join with a control table.

Outcome

Six mandatory analytical deliverables and two optional ones (periodic polling of votes and a bill-progress history with validity per bill, derived from the events), 48 automated tests across six modules and continuous validation on GitHub Actions. Public repository.

Lessons learned

  • API collection stays outside the cluster: calling the API takes seconds, and a running cluster waiting on retries charges for the idle time.
  • A watermark is not an attribute of the record: the audit travels in every row, and the last value seen per endpoint lives in a separate control state.

Sales lakehouse on AWS

A study of a Medallion pipeline on AWS with two sample files: orders in CSV and customers in JSON. The files land in raw/ on Amazon S3, a Glue Crawler registers the schema in the Data Catalog, and Glue jobs in PySpark write Bronze and Silver as Parquet. Gold is an Iceberg table updated by MERGE in Athena, and consumption goes through Athena, Redshift Serverless and Power BI. Step Functions chains the Bronze and Silver Glue jobs; Lake Formation, IAM and CloudWatch handle access and monitoring.

Scope statement: the study consists of the architecture diagram and step-by-step guides per service. The study notes record execution in a personal AWS account up to Silver: files in raw/ on S3, the crawler, Athena queries on the raw layer and the Bronze and Silver Glue jobs. Gold on Iceberg, Redshift, Power BI, Step Functions, Lake Formation and CloudWatch exist only as documentation, not run, and carry the "Documented" tag in the diagram. The data is fictitious (8 orders) and there is no public evidence of the execution.

Technical decisions

  • Gold on Iceberg, updated by MERGE. MERGE in Athena (engine v3) also writes new data files and delete files; what Iceberg adds is the atomic commit in the metadata. Gold moves from one snapshot to the next in one step, and readers never see the swap halfway. With plain Parquet, the way out would be INSERT OVERWRITE or recreating the table, without that isolation.
  • Parquet from Bronze on. Athena charges per TB scanned, and a columnar format cuts what each query reads; with CSV until Silver, every query would read the whole file. Bronze changes only the format and stays faithful to the source, so it can be reprocessed.
  • One subfolder per dataset in raw/. The crawler catalogs by folder. Pointed above the subfolders, with Athena results written to the bucket root, it created junk tables in the Data Catalog. Pointed at raw/pedidos/ and raw/clientes/, it creates one table per dataset, which is where the Bronze job reads from.
  • Step Functions Standard, with .sync. .sync makes the state wait for the Glue job to finish before moving on, and only the Standard type offers that pattern; Express does not support it. Without it, Silver would read what Bronze had not written yet. Every state has Retry and Catch.
  • Lake Formation instead of direct S3 access. A column rule only holds if nobody reads the bucket from outside. IAM stops granting direct s3:GetObject on the layers, and reads go through the integrated engines (Athena, Glue, Redshift), which get temporary credentials from Lake Formation scoped to what was granted. Grants are by column and by layer LF-Tag (bronze, silver, gold), and hybrid access mode keeps existing IAM access working during the migration.

Outcome

Architecture and guides documented. Execution recorded up to Silver: a total revenue of 13,728.80 checked in Athena on the raw layer, 8 orders in Bronze and the Silver job run, with the Silver row count still to be checked. Gold, orchestration, Redshift and governance not executed.

Lessons learned

  • In the hands-on part, the catalog took more work than the ETL. The Data Catalog is regional, so a table that "disappears" is usually the console in another region; the crawler needs the exact subfolders; and Athena results need their own prefix (athena-results/), or the crawler catalogs them as a table.

DeliveredCorporate project · repository with the target architecture

Tax Document Processing Orchestration

The operator imports the tax spreadsheet into a Power Apps Canvas app. A cloud flow reads the file; the app shows a preview, sets aside rows with errors and writes the valid ones to Dataverse, in batches (one per establishment), with each invoice identified by its own key. When it closes a batch, the app sets three statuses on it that mark it as ready. The orchestrator, a manually triggered cloud flow, takes a ready batch and triggers an unattended Power Automate Desktop robot, which processes the batch invoices on the national NFS-e portal. The status contract plans for the robot to report the result back to the batch. The operator follows the statuses in the app.

Scope statement: what is described here is the production version: one unattended robot, batches selected by three statuses and deduplication by invoice key. The public repository is the target architecture for the next step, rebuilt without client data: time-bound batch claims, workers per portal category, protected evidence and automatic release of stuck runs. Nothing in it was exported from the real environment.

My role

With my team, I built the import, the Power Apps app, the Dataverse data model and the status contract with the robot. The orchestrator and the robot belong to another team, the automation team; on their side, I was responsible for what the app delivers and what the robot reads.

Technical decisions

  • An alternate key per invoice, without the tax period. Deduplication sits on the invoice (issue date, establishment, supplier and number), not on the file or the batch. Re-importing the same spreadsheet does not duplicate invoices. The tax period stays out of the key because it does not come from the invoice row: it is set at import, and the same invoice imported with another period would become a duplicate.
  • The app writes, after the preview. The app writes batches and invoices with Patch, instead of the server-side write flow, which stayed a draft. The preview shows the rows before writing, and an invoice with errors never reaches Dataverse. The cost is a busy screen while a large batch is written.
  • Three statuses per batch. The status used to be one per import, with the list of batches in a text field that overflowed its 500-character limit. Now each batch has its own: the app closes it with structure done, processing done and registration pending, and the orchestrator only selects that trio. The contract plans for the robot to mark registration as done when it finishes; on the robot side, that return has not been built yet.
  • Payload with the batch and the environment only. The orchestrator passes the batch name and the environment to the robot, and the robot fetches the invoices through their link to the batch, instead of receiving them in the call.

Outcome

In production: import through the app, batches and invoices in Dataverse, ready batches processed by the robot and batch statuses on the operator screen. Volume and cycle time are not published.

Lessons learned

  • Between two teams, three agreed statuses per batch kept things aligned better than the architecture document: the robot that reached production was simpler than the design, and the contract still held.
  • Two triggers in a row take the same batch: the three-status filter returns only the first one, and the status only changes when the batch finishes. One batch at a time is enough with one robot and one trigger at a time; with concurrency, the time-bound claim of the target architecture comes in.

DeliveredCorporate project · anonymized case

OTP authentication RPA with OIDC token persistence

A Power Automate Desktop robot that renews OIDC tokens for multiple accounts. It uses HTTP wherever an API exists and falls back to the browser only for login, OTP and token capture; it hands the token to another team's token service, which keeps it with a TTL, and verifies the write by reading it back.

Evidence and limits: in production, after end-to-end validation in the acceptance environment, with multi-account processing, failures isolated per account and operational error classification. The public case keeps environments, portals, endpoints and credentials anonymized.

Technical decisions

  • HTTP where an API exists, browser only where it doesn't. OAuth2 authentication, the account list, the OTP lookup and the token write are HTTP calls; the browser steps in for login, OTP and reading localStorage. Every step kept out of the browser is a step that doesn't break when the portal changes a CSS class.
  • Failure isolated per account. Each account runs inside an error-handling block: an invalid password or a missing OTP doesn't bring the whole run down, and the final summary classifies failures by cause.
  • Verify after writing. After the PUT, a GET confirms the token is readable by the integrations: persistence only counts once it has been read back.

Outcome

In production. During acceptance testing, each run covered about twelve accounts, with a cycle of roughly 70 seconds per account. Real production volume is not published.

Lessons learned

  • With ROPG blocked, a token born in the browser and a short-lived OTP, there is only one possible order (login, challenge, lookup and typing), and the whole flow was designed from it.
  • Mapping during validation what the API already solved kept half of the steps out of the browser.
